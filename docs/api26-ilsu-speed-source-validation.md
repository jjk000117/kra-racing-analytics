# API26 `ilsu`와 속도·구간기록 원천 검증

검증일: 2026-08-08  
상태: 소수 표본·기존 API4 원장 검증 완료, Snapshot·대량 수집 미실행

## 결론

- API26의 `ilsu`는 말의 휴식일수가 아니라 **경마장·경주일 단위의 `경주일수`**다. 공식
  메타데이터도 이보다 구체적인 산식은 제공하지 않는다. 말의
  `days_since_last_start` 또는 `days_since_last_finish`로 사용하지 않는다.
- 첫 Snapshot에 즉시 추가할 API26 계열 후보는 `rating` 하나다. 이미 API4 staging에 있으므로
  추가 API 수집은 필요 없다.
- 개별 과거 경주의 최종기록, S1F·G3F·G1F, 코너 기록, 거리, 경마장, 날씨, 주로·함수율,
  마체중, 착차의 원천은 현재 API4 데이터에 이미 있다. `race_date < feature_as_of`로 직접
  집계하면 Historical PIT Feature를 만들 수 있다.
- API37 마필 구간별 경주기록은 최고·최저·평균 누적값이고 공식 설명상 요청 경주일을 포함한다.
  현재 경주의 결과를 포함할 수 있어 Feature 원천으로 사용하지 않는다.
- 속도·페이스 Feature는 기준모델 이후 고도화로 미룬다. 거리·경마장·주로·경주 전개가 달라
  단순 `distance / race_time`을 최종 속도지수로 확정하지 않는다.

## 2. `ilsu` 의미 검증

### 공식 정의

API26 공식 메타데이터와 명세가 제공하는 이름은 `경주일수`뿐이다. 직전 출전일, 휴양일수,
양 끝 날짜 포함 여부와 같은 상세 산식은 제공하지 않는다.

### 실제 데이터 대조

API26 8개 표본의 `ilsu`는 API4의 같은 경주 행과 8/8 일치했다. 과거 이력이 있는 6개 표본은
다음과 같았다.

| API26 `ilsu` | 직전 실제 출전 후 일수 | 직전 정상 완주 후 일수 |
|---:|---:|---:|
| 88 | 21 | 21 |
| 39 | 14 | 14 |
| 94 | 36 | 36 |
| 73 | 42 | 42 |
| 42 | 23 | 23 |
| 97 | 14 | 14 |

차이가 14~73일이어서 양 끝 날짜 포함 여부로 ±1을 조정해도 일치하지 않는다. 첫 관측 2건은
API4 관측창 이전 이력이 없어 간격 비교에서 제외했다.

전체 API4에서도 같은 경마장·날짜 안의 `ilsu`는 605/605일 모두 단일값이었다. DNS 659행,
주행중지 134행, 실격 3행에도 모두 값이 존재했다. 직전 이벤트가 각각 DNS·주행중지·실격인 뒤
다음 완주 사례에서도 `ilsu`와 실제 간격은 다음처럼 달랐다.

| 직전 상태 | 실제 간격 | 다음 경주의 `ilsu` |
|---|---:|---:|
| `DNS` | 21일 | 10 |
| `RACE_STOPPED` | 14일 | 6 |
| `DISQUALIFIED` | 33일 | 87 |

경마장·연도별 관측 경주일의 단순 `dense_rank`와는 605일 중 108일이 달랐다. 따라서 현 데이터만으로
공식 캘린더의 정확한 번호 부여 산식까지 복원하지 않는다.

### 판정

`ilsu`는 **말 이력과 무관한 경주일 캘린더 속성**이다. `days_since_last_start`의 검증 원천도
아니며 첫 Snapshot에는 추가하지 않는다. 날짜·월·연도와 중복되는 약한 일정 신호로만 후속 검토할
수 있고, 현재는 분류 3(중복 또는 가치 낮음)이다.

## 3. API26 나머지 필드 재분류

조건·상금 관련 중복 필드 12개는 기존 8개 표본에서 API4와 8/8 일치했다. `stTime`과 `prd`는
API26 표본에서 날짜별·말별 값을 확인했지만 API4 현재 스키마에는 직접 대응 필드가 없다.

| 분류 | 필드 | 판단 | 현재 보유 / 추가 수집 |
|---|---|---|---|
| 1. 첫 Snapshot 추가 권장 | `rating` | 경주별로 달라지고 8/8 API4 일치. 말의 현재 능력 등급 신호 | API4 staging에 있음 / 불필요 |
| 2. 후속 Feature 후보 | `ageCond`, `sexCond`, `prizeCond`, `budam`, `rcName`, `chaksun1..5` | 현재 경주의 사전 조건·상금 규모. 등급·거리와 중복 및 희소 범주 효과를 기준모델 이후 검증 | API4에 있음 / 불필요 |
| 2. 후속 Feature 후보 | `stTime` | 시간대·경주 순서·기온 변화의 프록시가 될 수 있으나 첫 최소 모델 가치 불명확 | API26에 있음 / 채택 시 필요 |
| 2. 후속 Feature 후보 | `prd` | 산지·품종 배경 후보. 표본에서는 `한국`, `한국(포)` 확인 | API26에 있음 / 채택 시 필요 |
| 3. 중복 또는 가치 낮음 | `owNo` 마주 ID | API4에 이미 있고 첫 기준모델에서 마주 이력은 제외 | API4에 있음 / 불필요 |
| 3. 중복 또는 가치 낮음 | `ilsu`, 경주일·번호·거리·두수·마번·성별·연령·부담중량·관계자 ID | 현재 28개 명세 또는 기존 기본정보와 중복 | API4에 있음 / 불필요 |
| 4. PIT 위험·사용 불가 | `rcCntT/Y`, `ord1/2/3CntT/Y`, `chaksunT/Y/_6m` | 과거 조회에서도 현재·사후 누적값이 반환됨 | 수집하지 않음 |

`rating` 추가는 이번 검증의 권장 범위이며, 사용자가 Feature 범위를 승인하기 전까지 기존
28개 Snapshot 명세 자체는 변경하지 않는다.

## 4. 속도·구간기록 API와 실제 필드

### API4_3 경주기록 정보 — 기본 원천으로 권장

공식 메타데이터는 개별 출전마별 경주기록, 마체중, 착차, 경주로 구간기록과 경주 조건을 제공한다고
명시한다. 현재 staging에서도 다음 원문을 확인했다.

| 개념 | 현재 필드 | 가용성·주의 |
|---|---|---|
| 최종 경주기록 | `rcTime` | 서울 27,917/28,002, 부경 20,473/20,522가 0이 아닌 값. `0`은 상태·결측 센티널 처리 필요 |
| S1F/G3F/G1F | 서울 `seS1fAccTime`, `seG3fAccTime`, `seG1fAccTime`; 부경 `buS1fAccTime`, `buG3fAccTime`, `buG1fAccTime` | 경마장별 필드 사용. 반대 경마장 필드는 전부 `0` 센티널 |
| 1C/2C/3C/4C | 서울 `se_1cAccTime`~`se_4cAccTime`; 부경은 거리구간·G구간 필드 | 거리별 미통과 구간도 `0`; 단순 결측률로 해석 금지 |
| 구간 순위 | 서울 `sjS1fOrd`, `sjG3fOrd`, `sjG1fOrd`; 부경 `buS1fOrd`, `buG3fOrd`, `buG1fOrd` | 비표준 순위 코드 99를 상태와 함께 해석 |
| 거리·경마장 | `race.distance_m`, `race.meet_code` | 현재 Canonical에 있음 |
| 날씨 | `weather` | valid-start 전 행에 원문 존재 |
| 주로·함수율 | `track` | `건조 (2%)`, `다습 (10%)` 형태. 상태와 함수율 분리 파싱 가능 |
| 마체중·증감 | `wgHr` | `377(-10)`, `388(+1)` 형태로 전 행에 존재. 현재 Canonical NULL은 원천 부재가 아니라 파서 미구현 |
| 착차 | `diffUnit` | `-`, 숫자, `10+¾` 등 혼합 문자열. 전용 파싱과 비완주 상태 처리가 필요 |

API4는 개별 과거 경기 이벤트이므로 현재 경기 행을 쓰지 않고
`historical.race_date < feature_as_of`를 강제하면 최근 N회, 동일·유사 거리, 동일 경마장·거리,
과거 최고·평균, 주로상태별 기록을 직접 계산할 수 있다. 집계에는 정상적으로 기록이 존재하는
과거 출전만 사용하고 DNS·주행중지·실격과 `0` 센티널을 기록 평균에서 제외해야 한다.

### API37_1 마필 구간별 경주기록 — 모델 원천으로 사용 금지

API37은 거리별 최고·최저·평균 최종기록과 S1F, 1C~4C, G3F, G1F를 제공한다. 그러나 공식 설명이
**입력 경주일을 포함한 이전 경주**를 집계한다고 명시한다. 조회·정정 시점과 포함 행을 재구성하기
어렵고 현재 경주 결과가 들어갈 수 있으므로 Historical PIT Feature로 승인하지 않는다.

### API6_1 경주 구간별 성적 정보 — 후속 경주 페이스 맥락

경주 단위 1F~12F 구간기록, 1F~10F 통과거리·기록·순위를 제공한다. 개별 말 Feature보다는 과거
경주의 전체 페이스·전개 맥락을 만드는 후속 후보이며, 사용 시에도 과거 경주만 조인한다.

### API214_1 경주성적정보 — 대체·대조 원천

S1F/G3F/G1F, 1C~4C, 마체중, 착차를 명시적으로 제공하지만 현재 API4와 큰 폭으로 중복된다.
API4 원문의 구조·누락이 실제로 부족할 때만 소수 대조 검증한다. 지금은 추가 수집하지 않는다.

## 5. Historical PIT 위험과 단계 구분

| 데이터 | PIT 판정 | 첫 Snapshot | 추가 수집 |
|---|---|---|---|
| API4 과거 개별 경주 기록·구간·조건 | `race_date < feature_as_of`이면 사용 가능 | `rating`만 즉시 추가 권장 | 불필요 |
| API4 과거 속도·페이스·마체중·착차 | 직접 재계산 가능. 파싱·조건 보정 필요 | 기준모델 이후 | 불필요 |
| API26 경주별 조건·출발시각·산지 | 과거 경주별 값은 유효해 보이나 일부는 API4로 대조 불가 | 기준모델 이후 | 채택 필드가 API26 전용이면 필요 |
| API26/API37 누적·집계값 | 현재·당일 결과 혼입 위험 | 사용 금지 | 불필요 |
| API6 과거 경주 전체 페이스 | 과거 이벤트로만 조인하면 가능 | 기준모델 이후 | 채택 시 필요 |

첫 Snapshot의 변경 후보는 `rating` 하나다. 속도·구간기록, 마체중, 날씨·주로 적합성, 착차,
출발시각, 산지, 경주 조건 확장은 첫 기준모델의 날짜순 검증과 Calibration이 완성된 뒤 동일 분할의
ablation으로 판단한다.
