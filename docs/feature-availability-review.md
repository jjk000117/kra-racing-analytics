# 6B 연승 Feature 가용성 검토

검토일: 2026-08-02  
상태: 데이터 점검 완료, 모델·Feature Snapshot 미구현

> 후속 DNS 검증에서 DNS 말만 제외하고 605경주는 유지하는 것으로 정책을 확정했다. 이 문서의
> DNS 없는 민감도 집합은 주 모집단 대안이 아니라 선택적 비교 집합으로 해석한다. 상세 근거는
> `docs/dns-population-policy-validation.md`에 있다.

## 결론

현재 데이터만으로 **첫 확률모델의 개발용 데이터셋**은 만들 수 있다. 완료 상태이고 공식 연승
결과가 있는 4,582경주에서 사후 `is_valid_start`를 프록시로 사용하면 48,524개 출전마 행과
13,740개 양성 타깃을 구성할 수 있다. 공식 적중마가 출전마와 결합되지 않는 경우는 0건이다.

그러나 이 모집단은 발매 마감 당시의 베팅 가능 출전표를 직접 관찰한 것이 아니다. DNS 659행이
있는 경주가 605개로 전체의 13.2%이므로, 이 데이터만으로 실제 운영 시점의 스코어링 대상을
완전히 복원했다고 주장할 수 없다. 첫 모델을 파이프라인·시간순 검증·Calibration 완성 목적의
개발 모델로 한정한다면 다음 두 모집단을 병행하는 것이 가장 단순하다.

- 주 개발 집합: 4,582경주, `is_valid_start = true`인 48,524행
- 선택적 민감도 집합: DNS가 없는 3,977경주, 42,632행

실제 베팅 운영 또는 수익성 백테스트로 넘어가기 전에는 발매 마감 시점의 출전·취소 상태를
확인할 수 있는 사전 스냅샷이 필요하다.

## 1. 베팅 가능 출전마 모집단 확인 방법

### 현재 데이터로 확인 가능한 범위

1. `canonical.race.race_status = 'COMPLETED'`인 경주를 선택한다.
2. `canonical.winning_payout.pool_code = '연식'`인 공식 적중 결과가 존재하는지 확인한다.
   `연식`은 Canonical의 API 원문값이며 Star Schema의 표준 코드는 `PLC`다.
3. `canonical.runner_result`에서 `is_valid_start = true`인 말을 개발용 프록시 모집단으로 둔다.
4. `RACE_STOPPED` 133행과 `DISQUALIFIED` 3행은 실제 출전했으므로 음성 가능 행으로 보존한다.
5. DNS 659행은 모집단에서 제외하되, DNS가 하나라도 있는 605경주를 별도 표시한다.
6. 공식 연승 적중마를 `race_id + gate_no`로 결합하고 미결합·중복·invalid-start 양성이 0인지
   검사한다.

### 측정 결과

| 항목 | 결과 | 해석 |
|---|---:|---|
| 완료·공식 연승 경주 | 4,582 | 타깃 생성 가능 경주 |
| 전체 결과 행 | 49,183 | DNS 등 비출전 상태 포함 |
| 개발용 valid-start 행 | 48,524 | 사후 프록시 모집단 |
| 공식 연승 양성 | 13,740 | 양성률 28.32% |
| 공식 양성 미결합 | 0 | 타깃 결합 무결성 확인 |
| DNS | 659행·605경주 | 발매 마감 당시 대상 여부 불명확 |
| DNS 없는 민감도 집합 | 3,977경주·42,632행 | 모집단 불확실성 축소 |
| 주행정지 | 133행·119경주 | 실제 출전으로 보존 |
| 실격 | 3행·3경주 | 실제 출전으로 보존 |

### 사용할 수 없는 해석

- `is_valid_start = true`가 발매 마감 시점의 공식 출전표였다고 단정하지 않는다.
- DNS를 단순한 음성 타깃으로 바꾸지 않는다.
- DNS가 있는 경주 전체를 근거 없이 주 학습 집합에서 영구 제외하지 않는다.
- 현재 결과 API만으로 취소 공지시각, 환불 여부와 발매 대상 변경시점을 추정하지 않는다.

## 2. Feature 후보

6A 분류 원칙에 따라 실제 후보를 다음처럼 정리한다. `현재 보유`는 컬럼이 있다는 뜻이며, 현재
경주의 값이 발매 마감 전에 이용 가능했다는 뜻은 아니다.

### A. 현재 보유한 기본 후보

| 범주 | 후보 | 현재 상태 | 6B 판정 |
|---|---|---|---|
| 경주 식별·시간 | 경주일, 경마장, 경주번호 | 결측 없음 | 관리키·분할키, 일부 범주형 후보 |
| 경주 조건 | 등급, 거리 | 결측 없음 | 사전 가용성 확인 후 사용 후보 |
| 경주 규모 | 등록두수 | 결측 없음 | 발매 대상 두수와 다르므로 보조 후보 |
| 출전마 | 말 ID, 마번, 성별, 연령 | 결측 없음 | 사전 가용성 확인 후 사용 후보 |
| 관계자 | 기수·조교사·마주 ID | 결측 없음 | ID 자체보다 과거 이력 집계키로 사용 |
| 부담 조건 | 부담중량 | 결측 없음 | 사전 가용성 확인 후 사용 후보 |
| 마체 상태 | 마체중 | 48,524행 전부 결측 | 현재 데이터에서는 사용 불가 |
| 당일 환경 | 날씨, 주로상태 | 컬럼 존재 | 관측시각 불명확으로 보류 |
| 시장 정보 | 단승·연승배당 | 결과 API 값 | 현재 경주 Feature 사용 금지 |
| 사후 결과 | 착순, 경주기록, 결과상태 | 완전 또는 상태별 존재 | 타깃·과거 이력에만 사용, 현재 행 금지 |

### B. 과거 이력으로 생성 가능한 후보

모든 집계는 `history_race_date < current_race_date`를 지켜야 한다.

| 범주 | 후보 예시 | 우선도 | 주의사항 |
|---|---|---|---|
| 말 경력 | 과거 출전수, 첫 출전 여부, 휴식일수 | 높음 | 수집 시작 전 이력은 알 수 없음 |
| 말 성적 | 승·연승·3착 이내 비율, 유효 완주율 | 높음 | 분모와 상태정책 고정 필요 |
| 최근 폼 | 최근 3·5회 착순·연승·경주기록 요약 | 높음 | 이력 부족 플래그 필요 |
| 조건 적합성 | 거리·경마장·등급별 과거 성적 | 높음 | 표본 수와 함께 사용 |
| 기수 성적 | 과거 출전수, 승·연승률, 최근 폼 | 높음 | 동일 날짜 결과 제외 |
| 조교사 성적 | 과거 출전수, 승·연승률, 최근 폼 | 높음 | 동일 날짜 결과 제외 |
| 조합 이력 | 말–기수, 기수–조교사 과거 성적 | 중간 | 희소성과 과적합 주의 |
| 부담 변화 | 직전 대비 부담중량, 조건별 부담중량 성적 | 중간 | 현재 부담중량의 사전 가용성 필요 |
| 경주기록 | 거리 보정 기록, 개인 최고·최근 기록 | 중간 | 과거 결과만 사용하고 조건 보정 필요 |
| 마주 성적 | 과거 출전수와 성적 | 낮음 | 첫 기준모델에는 필수 아님 |

이력 깊이 점검에서 말 과거 출전이 없는 행은 4,973개(10.25%), 기수는 334개(0.69%),
조교사는 249개(0.51%)다. 중앙 과거 출전수는 말 6회, 기수 328회, 조교사 320회다. 데이터가
2024년부터 시작하므로 실제 데뷔가 아니라 관측창의 좌측 절단일 수 있다. 따라서 `prior_count`,
`history_available`, `history_complete`를 값과 함께 관리해야 한다.

### C. 처음부터 제외할 현재 경주 정보

- 공식 착순과 연승 적중 여부를 제외한 결과 파생값
- 현재 경주 `race_time`
- 현재 경주 `result_status`, `is_valid_start`, `is_valid_finish`
- 현재 경주 단승·연승배당
- 매출, 확정배당과 환급 관련 값

이 값들은 모집단·타깃 생성 또는 사후 평가에는 쓸 수 있지만 모델 입력에는 들어가지 않는다.

## 3. 부족한 정보의 필수·선택 구분

정보가 경마에서 일반적으로 중요해 보인다는 이유만으로 API를 추가하지 않는다. 아래 단계로
판정한다.

### 판정 등급

| 등급 | 판정 질문 | 처리 |
|---|---|---|
| 계약 필수 | 없으면 예측 행·타깃·시점을 올바르게 정의할 수 없는가? | 구현 전 확보 또는 명시적 연구용 프록시 승인 |
| 기준모델 우선 | 현재 데이터로 안전하게 만들 수 있고 강한 도메인 근거가 있는가? | 첫 Feature Snapshot 후보 |
| 성능 고도화 | 모델은 성립하지만 추가 설명력을 기대할 수 있는가? | 기준모델 이후 ablation으로 판단 |
| 있으면 좋음 | 활용가치는 불확실하고 수집·시점관리 비용이 큰가? | 수집 보류 |

### 현재 판정

#### 계약 필수

- 안정적인 `race_id`, `horse_id`, 경주일과 말 단위 타깃 연결
- 공식 연승 적중 결과
- 예측시점보다 이전인 이력 경계
- 실제 운영·베팅 주장을 할 경우 발매 마감 시점의 출전마 목록, 취소 상태와 가용시각

앞의 세 항목은 현재 데이터로 충족한다. 마지막 항목은 충족하지 못한다. 따라서 현재 데이터는
개발 모델에는 사용할 수 있지만 실제 베팅 가능 모집단을 완전히 복원한 운영 데이터로는 부족하다.

#### 기준모델 우선

- 말·기수·조교사의 과거 출전수와 연승 관련 성적
- 최근 폼과 휴식일수
- 거리·경마장·등급 조건 경험
- 경주 조건과 출전마의 기본 정보 중 사전 가용성이 확인된 항목
- 이력 부족과 관측창 불완전 플래그

#### 성능 고도화

- 마체중과 증감
- 당일 주로상태·날씨의 시점 확인값
- 말–기수 등 조합 이력
- 더 긴 과거 이력
- 예측 마감 전에 저장된 시장 배당 스냅샷을 사용하는 별도 시장인지 모델

#### 있으면 좋음

- 혈통·조교·장구·세부 구간기록 등 아직 기준모델의 추가가치를 측정하지 않은 정보
- 마주 중심의 세밀한 파생지표
- 가용시점이나 수정 이력을 재구성하기 어려운 정보

### 추가 수집 승인 규칙

추가 정보는 다음을 모두 만족할 때만 수집 대상으로 제안한다.

1. 현재 데이터로 대체할 수 없다.
2. 발매 마감 전 가용시점을 재현할 수 있다.
3. 학습 과거 전체에 일관된 범위로 확보할 수 있다.
4. 업무키와 수정·취소 이력을 추적할 수 있다.
5. 계약 필수이거나 기준모델 대비 성능 개선을 검증할 구체적 실험이 있다.

## 권장 다음 결정

첫 모델의 원래 목적이 Feature 파이프라인, 날짜순 검증과 Calibration 구조 완성이므로, 추가 API
수집 전에 다음 개발 범위를 승인하는 것을 권장한다.

- 48,524행 valid-start 프록시를 주 개발 집합으로 사용
- DNS 말만 제외하고 DNS가 있는 정상 경주는 유지
- DNS 없는 42,632행은 선택적 모집단 민감도 집합으로 사용
- 결과를 실제 발매 마감 모집단 기반 운영 성능으로 표현하지 않음
- 현재 데이터로 가능한 기준 Feature만 먼저 설계·구현
- 추가 API는 기준모델 결과와 실제 운영 필요성을 본 뒤 결정

이 범위가 승인되면 다음 단계는 **6C Feature Snapshot 명세와 구현**이다.
