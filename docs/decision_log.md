# 의사결정 기록

중요한 설계 변경과 범위 결정을 날짜순으로 기록한다. 새로운 결정을 추가할 때 기존 기록을
삭제하거나 현재 결론에 맞춰 소급 수정하지 않는다. 결정이 바뀌면 새 항목으로 남긴다.

## 2026-08-01 — 기존 저장소를 읽기 전용 참고자료로 사용

결정:

- `horse_racing`은 정책과 과거 구현을 확인하는 읽기 전용 자료로만 사용한다.
- 생성·수정·삭제·Commit·Push는 `kra-racing-analytics`에서만 수행한다.

이유:

- 기존 R 프로젝트의 재현성과 이력을 보존하면서 Python + SQL 기반의 독립적인 프로젝트를
  구축하기 위해서다.

## 2026-08-01 — Python 환경은 기존 Anaconda의 별도 Conda 환경 사용

결정:

- 기존 Anaconda 설치를 사용하되 프로젝트 전용 `kra-racing-analytics` 환경을 만든다.
- VS Code는 필수 도구로 채택하지 않는다.
- JupyterLab은 탐색과 분석에 사용한다.

이유:

- base 환경 오염을 막고 사용자가 익숙한 Anaconda 환경에서 재현 가능성을 유지하기 위해서다.

## 2026-08-01 — 초기 데이터베이스로 DuckDB 채택

결정:

- 초기 SQL 저장소는 로컬 파일 기반 DuckDB를 사용한다.
- SQL Server나 외부 서버형 DB는 현재 범위에 포함하지 않는다.

이유:

- 별도 서버 운영과 라이선스 비용 없이 Python·Jupyter·SQL 분석을 빠르게 시작할 수 있고,
  향후 Star Schema와 Power BI 연결에 필요한 SQL 구조를 학습할 수 있기 때문이다.

## 2026-08-01 — Raw 증거를 먼저 보존하고 Staging에 적재

결정:

- API 응답 원문은 불변 파일로 보존한다.
- request_id, batch_id, SHA256, 수집시각을 Manifest에 기록한 뒤 SQL Staging에 적재한다.
- Canonical 검사는 Staging 적재 후 별도 테이블을 생성하는 방식으로 수행한다.

이유:

- 원문 추적, 재처리, 변환 버전 비교와 향후 증분·자동 운영 확장을 가능하게 하기 위해서다.

## 2026-08-01 — 초기 운영은 수동 전체 재구축

결정:

- 최신 증분 수집과 자동 운영은 후속 단계로 미룬다.
- 초기에는 과거 범위 전체를 수동으로 재구축한다.

이유:

- 데이터 계약과 상태 정책을 먼저 안정화하고 초기 프로젝트 복잡도를 제한하기 위해서다.

## 2026-08-02 — 경주 단위 상태가 출전마 상태보다 우선

결정:

- 2024-09-29 서울 2경주와 2025-12-26 부산경남 6경주는 `RACE_CANCELLED`로 관리한다.
- 2026-07-06의 확인된 9경주는 `RESULT_NOT_FINALIZED`로 관리한다.
- 경주 취소·결과 미확정 상태는 해당 경주의 모든 출전 결과에 우선 적용한다.

이유:

- `ord` 단일 값만으로 서로 다른 경주 수준의 상황을 확정할 수 없으며, 경주 전체 상태가
  공식 순위의 유효성을 결정하기 때문이다.

## 2026-08-02 — 취소 사유는 분석 상태에서 분리

결정:

- 분석 상태는 `RACE_CANCELLED`로 통일한다.
- 다량 낙마 같은 구체적인 사유는 `evidence_note`에만 보존한다.
- Canonical 경주 본문에는 `status_reason`을 두지 않는다.

이유:

- 취소 사유를 모든 경주에서 일관되게 수집할 수 없고, 사유별 상태값 증가가 분석을
  불필요하게 복잡하게 만들기 때문이다.

## 2026-08-02 — 시장 분석 모집단은 4,582경주

결정:

- 정상 완료되고 공식 7개 승식 매출이 모두 있는 경주만 시장 분석 Mart에 포함한다.
- 취소·결과 미확정·매출 누락 경주는 Fact에 보존하고 Mart에서만 제외한다.
- 매출 없는 경주를 0원으로 대체하지 않는다.

이유:

- 완전한 승식 간 비교를 보장하면서도 제외된 원천과 이유를 추적하기 위해서다.

## 2026-08-02 — 모든 등급과 승식을 보존한 뒤 분석으로 범위 결정

결정:

- 현재 관측된 10개 등급을 모두 분석한다.
- 7개 승식을 모두 Star Schema와 시장 분석에 포함한다.
- 연승식·복승식은 관심 후보지만 분석 전에 모델 후보로 확정하지 않는다.

이유:

- 사전 선택으로 시장 구조를 왜곡하지 않고 월·경마장·등급·승식 비교 결과를 근거로 후속
  범위를 정하기 위해서다.

결정:

## 2026-08-02 — 시각화 도구는 최종 보고서 단계에서 확정

결정:

이유:

- 데이터 모델과 분석 질문을 먼저 안정화하고 시각화 도구에 종속되는 조기 결정을 피하기
  위해서다.

## 2026-08-02 — 공식 적중배당은 조합 단위로 정규화

결정:

- 정규화 목표 Grain은 `경주 × 승식 × 공식 적중 조합`으로 한다.
- 동착으로 한 경주·승식에 여러 공식 조합이 있어도 모두 별도 행으로 보존한다.
- 쌍승식·삼쌍승식은 마번 순서를 보존하고, 복승식·복연승식·삼복승식은 정렬된 canonical
  조합을 함께 저장한다.
- `confirmed_odds_raw`, 원문 내 순서와 lineage를 보존한다.
- 확정배당은 모델 Feature가 아니라 시장 분석과 백테스트 정산에만 사용한다.

이유:

- 32,074개 원본 행에서 50,494개 적중 조합이 관찰됐고 동착 시 통상 단일 조합 승식에도
  2개 조합이 존재해 `경주 × 승식` Grain만으로는 정보가 손실되기 때문이다.

## 2026-08-02 — 연승식 적중 범위는 공식 배당 원문을 우선

결정:

- 연승식은 공식 원문에 기록된 1·2위 또는 1·2·3위 적중 조합을 그대로 보존한다.
- 경주결과 API의 등록두수나 최종 유효 출전두수만으로 적중 범위를 다시 계산하지 않는다.
- 감사에서는 연승 적중마가 공식 순위의 1·2위 또는 1·2·3위와 일치하는지만 확인한다.

이유:

- 8두 등록 후 제외마가 발생한 경주에서 연승 적중마 2두와 3두가 모두 관찰돼, 현재 데이터만으로
  발매 시점의 출주두수 기준을 확정할 수 없기 때문이다.

## 2026-08-02 — 승식 후보는 종합점수 대신 파레토 집합으로 관리

결정:

- 승식별 경주 수는 후보 비교 지표에서 제외한다.
- 매출 비중·나이브 적중확률은 높을수록, 가능 조합 수·배당 꼬리비율은 낮을수록 유리한
  파레토 축으로 사용한다.
- 연승식·복승식·복연승식·삼복승식을 비지배 후보로 유지한다.
- 단승식·쌍승식·삼쌍승식은 1차 후보에서 제외한다.
- 임의 가중치와 종합점수는 사용하지 않는다.

이유:

- 각 승식은 시장 규모와 예측 난도 사이의 서로 다른 절충점을 가지며, 가중치를 임의로 정하면
  사용자의 목적을 데이터가 대신 결정한 것처럼 보일 수 있기 때문이다.

## 2026-08-02 — 첫 모델은 연승식, 복승 기본안은 조합 직접 분류

결정:

- 첫 완성 모델은 연승식 적중 여부를 타깃으로 하는 `경주 × 출전마` 확률모델로 한다.
- 첫 모델의 목적은 Feature 파이프라인, 날짜순 검증, 확률평가와 Calibration 구조 완성이다.
- 복승식은 핵심 후속 목표로 유지하고 첫 구현은 비순서 2두 조합 직접 분류를 기본안으로 한다.
- 별도 결합모델과 순위 기반 공동확률 모델은 복승 기준모델 이후 비교 후보로 남긴다.
- 연승 모델 출력이 복승 조합확률로 자동 전환된다고 가정하지 않는다.

이유:

- 연승식은 첫 확률모델의 데이터·검증 구조를 완성하기에 단순하고 양성 표본이 상대적으로
  충분하다.
- 말별 연승 주변확률만으로 두 말의 복승 공동확률은 식별되지 않으므로 복승에는 별도의 조합
  확률모델이 필요하다.

## 2026-08-02 — 6A는 데이터 계약 원칙, Feature 목록은 6B에서 설계

결정:

- 6A에서는 Feature의 분류 원칙과 추가 API 필요성 판단 원칙만 정의한다.
- 실제 Feature 목록은 6B에서 설계한다.
- 실제 추가 API 목록과 수집 여부는 6B 이후 Feature 가용성 검토 결과를 바탕으로 결정한다.

이유:

- 데이터 계약과 구체적인 Feature 설계를 분리해 예측시점·누수 방지 원칙을 먼저 고정하면서도,
  현재 데이터의 가용성을 확인하기 전에 불필요한 API 수집 범위를 확정하지 않기 위해서다.

## 2026-08-02 — 연승 모델링 데이터 계약 확정

결정:

- 예측 Grain은 `경주 × 베팅 가능 출전마`, 타깃은 공식 PLC 적중마 여부로 한다.
- 운영 예측시점은 연승 발매 마감 직전으로 두며, 일 단위 이력은 경주일보다 이전 자료만 쓴다.
- 학습 경주는 완료 상태, 공식 PLC 적중 결과, 베팅 가능 모집단 복원 조건을 모두 만족해야 한다.
- 공식 PLC 원문으로 타깃을 생성하고 등록두수로 적중 범위를 다시 계산하지 않는다.
- Train·Validation·Final Test는 경주일 기준 연속 구간으로 분할하며 같은 경주를 나누지 않는다.
- Log Loss, Brier Score와 Calibration을 주 평가로 사용한다.
- 현재 `is_valid_start`를 발매 마감 당시 베팅 가능 여부와 동일하다고 간주하지 않는다.

이유:

- 공식 연승 결과를 보존하면서 사후 상태가 Feature나 예측 모집단에 유입되는 누수를 막기
  위해서다.
- 모델의 첫 목적이 베팅 수익 최적화가 아니라 재사용 가능한 확률모델 검증 구조의 완성이므로
  확률의 정확성과 보정 상태를 우선 평가한다.

## 2026-08-02 — 6B 모집단은 개발 프록시와 민감도 집합으로 구분

결정:

- 완료·공식 연승 경주의 `is_valid_start = true` 행을 첫 모델의 개발용 프록시 모집단으로
  제안한다.
- DNS가 없는 경주를 별도 모집단 민감도 집합으로 관리한다.
- 현재 프록시의 결과를 발매 마감 시점의 실제 운영 모집단 성능으로 표현하지 않는다.
- 부족한 정보는 계약 필수·기준모델 우선·성능 고도화·있으면 좋음의 네 단계로 판단한다.
- 추가 API는 현재 데이터 기준모델과 가용성 검토 없이 선제적으로 수집하지 않는다.

이유:

- 공식 타깃은 완전하게 결합되지만 DNS가 있는 605경주에서는 현재 결과 데이터만으로 발매 마감
  당시의 베팅 가능 여부를 입증할 수 없기 때문이다.
- 첫 모델의 목적은 운영 배치가 아니라 데이터·시간순 검증·확률평가 구조의 완성이므로 불확실성을
  명시한 프록시와 민감도 비교가 최소 구현에 적합하다.

## 2026-08-02 — DNS는 말 단위 제외, 정상 경주는 유지

결정:

- `result_status='DNS'`인 말은 모델링 행에서 제외하고 음성 타깃으로 만들지 않는다.
- DNS가 있다는 이유만으로 경주 전체를 제외하지 않는다.
- `RACE_STOPPED`, `DISQUALIFIED`는 실제 출전 행으로 유지한다.
- 경주 단위 제외는 취소·결과 미확정·공식 연승 누락·타깃 결합 실패·미해결 비출전 상태 등
  경주 전체의 학습 계약이 깨지는 경우로 제한한다.
- DNS 없는 3,977경주는 주 모집단 대안이 아니라 선택적 민감도 집합으로 유지한다.

이유:

- DNS 605경주 중 601경주(99.34%)는 1~2두 DNS였고 3두 DNS 4경주도 유효 출전마 8두로
  정상 진행됐다.
- 605경주 모두 완료 상태·7개 승식·1착·공식 연승 결과가 정상이며 경주 단위 이상은 0건이었다.
- 경주 전체를 제외하면 정상 출전마 5,892행을 불필요하게 잃고 선택 편향을 만들기 때문이다.

## 2026-08-08 — 첫 역사적 Feature Snapshot은 API4_3 최소 Feature로 구성

결정:

- 추가 API 없이 API4_3만으로 첫 역사적 Feature Snapshot을 만든다.
- 현재 기본정보 8개와 최소 Point-in-Time 이력 Feature 20개를 첫 모델 입력으로 사용한다.
- 실제 출전수에는 정상 완주·주행중지·실격을 포함하고 DNS는 제외한다.
- PLC 적중률은 공식 PLC 적중수/실제 출전수로 계산한다. 주행중지·실격은 실패로 포함하되
  착순 평균에서는 제외한다.
- 같은 날짜 결과는 전부 제외하고 `source_max_event_date < race_date`를 강제한다.
- Snapshot 구현 전 명세를 먼저 확정하며 이번 단계에서는 구현하지 않는다.

이유:
