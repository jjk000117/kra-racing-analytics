# 2C Raw Data Profiling

## 결론

2024-01-05~2026-07-26의 정식 전체 수집 배치를 검사했다. API4_3과 API179_1은 Staging 설계를 진행할 수 있을 만큼 구조가 안정적이다. 정식 배치 내부 업무 키 중복과 필수 키 결측은 0건이다. API179_1의 모든 경주는 API4_3에 결합되지만 API4_3 경주 중 18개에는 매출 데이터가 없다. 이 예외는 삭제나 임의 보완 없이 품질 이슈로 유지한다.

## 분석 범위

| 데이터 | 배치 | 파일 | 행 | 날짜 범위 |
|---|---|---:|---:|---|
| API4_3 | `20260801T152038430395Z_api4_3_34c281ed` | 51 | 49,386 | 2024-01-05~2026-07-26 |
| API179_1 | `20260801T153512893532Z_api179_1_9d682cd1` | 37 | 32,074 | 2024-01-05~2026-07-26 |

샘플 호출 파일도 Raw 증거로 보존되어 있지만 프로파일에서는 제외했다. Manifest에서 API별 완료 배치 중 요청 수가 가장 큰 전체 배치를 선택하므로 샘플과 전체 배치가 섞여 생기는 중복을 방지한다.

## Grain과 키 검사

| 검사 | API4_3 | API179_1 |
|---|---:|---:|
| 예상 grain | 경주 출전마 | 경주·승식 |
| 후보 업무 키 | `rcDate+meet+rcNo+hrNo` | `rcDate+meet+rcNo+pool` |
| 업무 키 중복 행 | 0 | 0 |
| 완전 동일 중복 행 | 0 | 0 |
| 필수 키 결측 | 0 | 0 |

API4_3은 4,600개 경주, API179_1은 4,582개 경주를 포함한다. 경주 결합 키는 `rcDate + meet + rcNo`다.

## 경주 결합 품질

| 지표 | 값 |
|---|---:|
| 공통 경주 | 4,582 |
| API4_3 기준 결합률 | 99.61% |
| API179_1 기준 결합률 | 100.00% |
| 경주 결과만 존재 | 18 |
| 매출만 존재 | 0 |

매출이 없는 18경주는 2024년 1경주, 2025년 1경주, 2026년 16경주다. 일부는 `ord`가 `0`, `92`, `94`, `99`인 비표준 결과를 포함하지만 정상 순위가 있는 경주도 있어 상태코드만으로 일괄 제거할 수 없다.

- 심각도: Medium
- 영향: 매출 분석이나 사후 베팅 평가에서 해당 18경주는 사용할 수 없다.
- 처리: `race_without_sales` 이슈로 기록하고 Canonical 결합은 left join으로 유지한다.
- 자동 검사: 매출 고아 경주는 0건이어야 하며 결과 대비 매출 결합률을 배치별로 기록한다.

## 필드와 값 도메인

API4_3은 전체 89개 필드 중 83개가 모든 행에 존재한다. 선택 필드의 원천 결측은 `owName` 35건, `owNameEn` 35건, `owNo` 35건, `trName` 35건, `trNameEn` 76건, `trNo` 35건이다. 필수 경주·출전 키에는 결측이 없다.

API179_1은 `amt`, `meet`, `odds`, `pool`, `rcDate`, `rcNo` 6개 필드가 모든 행에 존재한다. 매출 금액 `amt`의 음수·비숫자 형식은 0건이다. 다음 7개 승식이 각각 4,582행으로 모든 매출 경주에 정확히 한 번씩 나타난다.

- 단식
- 연식
- 복식
- 복연
- 쌍식
- 삼복
- 삼쌍

## Staging 설계 근거

API4_3 Staging은 출전마 한 행을 유지하고 89개 원천 필드, `source_row_number`, `request_id`, `raw_file_id`, `batch_id`, 적재시각을 보존한다. 초기 적재에서는 원천 문자열을 우선 보존하고 날짜·정수·금액 변환 성공 여부를 별도 품질 열로 기록한다.

API179_1 Staging은 경주·승식 한 행을 유지한다. `amt` 원문과 숫자 변환값을 함께 보존하고, `pool`은 7개 관측값을 허용 목록으로 검사한다. `odds`는 복합 문자열이므로 Staging에서 성급하게 분해하지 않고 Canonical 단계에서 승식별 규칙을 적용한다.

매출·확정배당은 post-race 데이터다. 예측 Feature와 물리적으로 분리하며 사후 시장 분석·베팅 평가에만 사용한다.
